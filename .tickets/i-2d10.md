DESIGN: Tuple Unpacking and Decomposition

PROBLEM: Accessing tuple elements requires verbose projection syntax (result.0, result.1, ...)

PROPOSED SYNTAX:
Basic: {a, b, c} = getTuple();

Partial: {a, b} = getTuple();  % getTuple() returns Tuple<int, string, double, bool>

Wildcards: {a, _, c} = getTuple();  % Ignore middle element

Nested: {a, {b, c}} = getNestedTuple();

For loops: for ({x, y} in pointList) { action(x, y) }

TYPE SYSTEM:
- {a, b, c} = expr where expr: Tuple<T1, T2, T3>
- a: T1, b: T2, c: T3
- Partial unpacking: {a, b} = expr where expr: Tuple<T1, T2, T3, T4, ...> OK
- Type mismatch: {a, b, c, d} = Tuple<int, int> ERROR (too many vars)

AST: N_UNPACKING_PATTERN node type
- degree: number of elements
- subtrees[i]: TK_VAR (variable), TK_UNDERSCORE (wildcard), or nested pattern

CODE GENERATION: Expand to tuple projections:
{a, b, c} = tuple  →  a = tuple.0; b = tuple.1; c = tuple.2;

IMPLEMENTATION PHASES:
1. Parser: recognize {var, var, ...} patterns in assignments
2. Type checking: validate tuple count and element types
3. Code generation: expand to projections
4. For-in loops: support unpacking patterns

EXAMPLES:
1. Query results: {fileName, size, lastMod} = queryFile(...)
2. Function returns: {x, y, z} = getCoordinates(id)
3. For loop: for ({key, value} in pairs) { process(key, value) }
4. Partial: {name, age} = getFullRecord();  % Ignore remaining

SCOPING: Variables follow standard scoping; loop vars are loop-scoped

PERF: Zero overhead (expands at compile-time), same performance as manual projections

ERROR MESSAGES:
- Non-tuple: Cannot unpack non-tuple type
- Count: Too many variables for tuple elements
- Type: Type mismatch after unpacking

BACKWARD COMPAT: New syntax, opt-in, no breaking changes

FUTURE: Spread operator ({head, ...tail}), destructuring objects, arrays
