# Design union type representation for safe type fallback


## Notes

**2026-01-12T19:23:30Z**

## Union Type Design

### Current State
- T_DYNAMIC is a wildcard type used everywhere (T_DYNAMIC = 200 in enum)
- T_VAR represents type variables with disjuncts (subtrees array)
- Existing macro T_VAR_DISJUNCT(x, n) accesses individual disjuncts
- Type system already has mechanism for disjunctive types

### Proposed Union Type Representation

**Option 1: Extend T_VAR for Union Types**
- Reuse existing T_VAR node type
- Existing subtrees array already holds disjuncts
- Existing T_VAR_DISJUNCT macros work as-is
- Label as 'union_T_DYNAMIC_T_INT' etc for clarity
- Minimal code changes required

**Option 2: New T_UNION Node Type**
- Add T_UNION = 208 to enum (between T_TUPLE and T_CONS)
- Similar structure to T_VAR but explicitly for union types
- Better semantic clarity in AST
- More changes to type checking code

**Recommendation: Option 1** (extend T_VAR)
- Already have disjunctive type support
- Minimizes changes to type inference
- Can label unions distinctly for clarity
- Simpler transition path

### Implementation Strategy

1. **Type Creation**: newUnionType(int arity, ExprType **types, Region *r)
   - Creates T_VAR node with multiple disjuncts
   - Each disjunct is a concrete type (T_INT, T_STRING, etc.)
   - Returns structure compatible with existing type system

2. **Type Checking**: Update typeExpression3()
   - When encountering N_QUERY, check column metadata
   - For known columns, return single-type tuple
   - For unknown columns, return newUnionType(T_DYNAMIC, T_STRING, etc.)
   - For N_ATTR, similar metadata lookup

3. **Constraint Solving**: Update simplify() and solveConstraints()
   - When unifying variable with union, constrain to matching disjunct
   - When operation on union (e.g., addition), require all disjuncts support it
   - Report errors for unsupported operations on partial unions

4. **Error Messages**: Add getUnionTypeName()
   - Format as 'union<T_INT|T_STRING|T_DYNAMIC>'
   - Improves diagnostic clarity

## Design Decisions

### Why T_VAR for Unions
- Leverages existing type variable infrastructure
- T_VAR already supports disjuncts via subtrees array
- Minimal changes to constraint solver (handles disjuncts already)
- Backward compatible with existing type system

### Union Type Semantics
- Union represents 'type A OR type B OR ...'
- Each disjunct must be a concrete type
- Union constraints narrow possibilities at usage time
- Operations on unions require all disjuncts support operation

### Error Reporting Format
- Format: 'union<Type1|Type2|...|TypeN>'
- Human-readable for policy developers
- Distinguishable from regular types in error messages
- Buffer-safe up to 512-char limit
